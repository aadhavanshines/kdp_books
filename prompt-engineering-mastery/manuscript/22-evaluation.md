# Chapter 22: Testing and Evaluating Prompts

A prompt that works once in a chat window is a prototype. A prompt that runs thousands of times in a product needs evidence that it works. **Evaluation**, or **evals**, is how professionals measure prompt quality, compare versions, and prevent regressions. It's the single practice that most separates hobbyist prompting from professional prompt engineering.

## Why Evaluate?

Without evaluation, prompt changes are guesses. You fix one problem and unknowingly create two others. You switch to a new model and don't notice that a critical behavior changed. You can't answer the question your manager will eventually ask: "How well does this actually work?"

Evaluation gives you:

- **A baseline:** How good is the current prompt?
- **Comparisons:** Is version B better than version A? Is the new model better than the old one?
- **Regression protection:** Did this change break anything that used to work?
- **Confidence to ship:** Evidence that quality meets the bar.

## Step 1: Define Success

Before testing, decide what "good" means for your task, as specifically as possible. Success criteria should be:

- **Specific:** "Responses correctly identify the customer's issue category," not "responses are good."
- **Measurable:** "At least 95% of extracted invoice totals match the source exactly."
- **Prioritized:** Which criteria matter most? A support bot's accuracy and safety likely matter more than its wit.

Common criteria include accuracy, faithfulness to sources, format compliance, tone, completeness, conciseness, safety, refusal appropriateness, and latency and cost.

## Step 2: Build a Test Set

A **test set** is a collection of inputs, ideally with expected outputs or grading notes, that represents real usage. Include:

- **Typical cases:** The common, everyday inputs.
- **Edge cases:** Empty inputs, very long inputs, unusual formats, multiple languages, ambiguous requests.
- **Hard cases:** Inputs where the prompt has failed before.
- **Adversarial cases:** Attempts to misuse the system or make it misbehave.

Where do test cases come from? Real user data (anonymized and with appropriate permission), cases written by domain experts, past failures, and, carefully, cases generated by a model and then reviewed by a person.

Start small. Even 20 to 50 well-chosen cases provide far more insight than none. Grow the set over time, adding every new failure you discover.

## Step 3: Choose Grading Methods

There are three main ways to grade outputs.

### Code-Based Grading

When outputs can be checked automatically, use code:

- Exact match: Does the classification equal the expected label?
- Format validity: Does the JSON parse? Are required fields present?
- Constraints: Is the summary under 100 words? Does it contain any banned phrases?
- Numeric accuracy: Does the extracted value match the source?

Code-based grading is fast, cheap, and objective. Use it wherever you can.

### Human Grading

People review outputs against a rubric. Human grading is the gold standard for nuanced qualities like helpfulness, tone, and subtle correctness, but it is slow and expensive. Use it for calibration, for high-stakes decisions, and to check that automated graders agree with human judgment.

### Model-Based Grading (LLM-as-Judge)

A language model grades outputs against a rubric. This scales human-like judgment to large test sets.

```
You are evaluating a customer support response.

<customer_message>{input}</customer_message>
<response>{output}</response>
<reference_policy>{policy}</reference_policy>

Grade the response on each criterion below as PASS or FAIL, with
a one-sentence justification:
1. Accuracy: Every factual claim is consistent with the reference
   policy.
2. Resolution: The response addresses the customer's actual
   question.
3. Tone: The response is polite and empathetic without being
   excessive.
4. Safety: The response doesn't promise refunds, which only human
   agents can approve.

Output JSON: {"accuracy": {"result": ..., "reason": ...}, ...}
```

For a response that offered the customer a refund, the grader might return:

```
{
  "accuracy": {"result": "PASS",
               "reason": "Matches the 30-day policy."},
  "resolution": {"result": "PASS",
                 "reason": "Explains how to start the return."},
  "tone": {"result": "PASS", "reason": "Polite and concise."},
  "safety": {"result": "FAIL",
             "reason": "Promises an unapproved refund."}
}
```

Run this across your whole test set, and you get a pass rate for each criterion, which tells you exactly what to fix next: here, a clearer instruction about refunds.

Making model graders reliable:

- **Use specific, binary or narrow-scale criteria.** "PASS/FAIL: mentions the 30-day return window" is more reliable than "Rate helpfulness 1-10."
- **Ask for reasoning before the verdict.**
- **Provide reference answers or source material** when possible.
- **Calibrate against humans:** Have people grade a sample, and check that the model grader agrees.
- **Watch for biases.** Model graders can favor longer answers, answers in certain positions when comparing two options, or answers from their own model family. When comparing two outputs, run the comparison in both orders.

## Step 4: Run, Compare, Iterate

With criteria, test set, and graders in place, the improvement loop becomes measurable:

1. Run the current prompt on the test set and record scores.
2. Analyze failures. Group them into patterns.
3. Change the prompt to address the biggest pattern.
4. Rerun the full test set.
5. Keep the change if overall scores improve without new regressions.

Because outputs vary, run each test case more than once for important decisions, and look at score distributions, not single runs.

> **Tip:** Read the outputs, not just the scores. Aggregate numbers hide patterns that are obvious when you read twenty failures side by side. The best prompt engineers spend a lot of time looking at real outputs.

## Evaluating in Production

Offline test sets don't capture everything real users do. Once a prompt is live:

- **Log inputs and outputs**, respecting privacy rules.
- **Collect user feedback**, such as thumbs up or down, corrections, and escalations to humans.
- **Sample and review** real conversations regularly.
- **Monitor metrics** such as error rates, refusal rates, response length, cost, and latency.
- **Feed failures back** into your test set.
- **A/B test** major changes on a fraction of traffic before full rollout.

## Evaluating Agents

Agents are harder to evaluate because they take many steps and there may be many valid paths to success. Approaches include:

- **Outcome-based grading:** Did the agent achieve the end state? For example, did the tests pass, was the correct record updated, or does the final answer match?
- **Trajectory review:** Were the steps reasonable, efficient, and safe?
- **Sandboxed environments** where agents can be tested repeatedly without real-world side effects.

## Tools for Evaluation

You can start with a spreadsheet: inputs in one column, outputs in another, grades in a third. As needs grow, many open-source frameworks and commercial platforms provide test management, automated grading, comparison dashboards, and production monitoring. Most AI providers also offer evaluation tools in their developer consoles. The tool matters less than the habit.

## Key Takeaways

- Evaluation turns prompt engineering from guesswork into measurable improvement.
- Define specific, measurable success criteria first.
- Build a test set of typical, edge, hard, and adversarial cases, and grow it from real failures.
- Grade with code where possible, models where needed, and humans for calibration.
- Iterate against the full test set, read real outputs, and keep monitoring in production.
