# Part IV: Practice

# Chapter 36: Four Full Mock Interviews

These four interviews replay complete system design rounds as conversations. The prompts are new, not repeats of Part III, so you can practice on them first: read only the prompt, set a timer for 40 minutes, and design out loud on paper. Then read the conversation and compare your clarifying questions, estimates, design and trade-offs.

Each interview targets a different level, and ends with the interviewer's notes, the kind of written feedback that goes to a hiring committee or debrief.

## Mock 1: Photo Sharing (Mid-Level)

**The prompt:** "Design a photo-sharing app: users upload photos and see photos from people they follow."

**Candidate:** Before I start, I'd like to pin down scope. I'm thinking: upload a photo with a caption, follow other users, and a home feed of photos from people you follow, newest first. I'll leave out comments, stories, messaging and search unless you want them. Does that work?

**Interviewer:** Yes. Add likes, but only as a count.

**Candidate:** Got it. How many users should I design for?

**Interviewer:** You decide.

**Candidate:** I'll assume 10 million uploads a day, about 2 MB each, 100 views per photo on average, and photos kept for five years with three copies. That gives about 116 uploads per second and about 11,600 views per second on average, roughly 35,000 at peak. Storage is about 110 PB over five years with three copies. View bandwidth is around 23 GB per second. So it's very read-heavy, the images can't live in a database, and we need a CDN.

**Interviewer:** Good. What does the API look like?

**Candidate:** Three main calls: `POST /photos` to upload, which returns a photo ID; `GET /feed?cursor=` for the feed, cursor-paginated so new photos don't make pages repeat; and `POST /photos/{id}/like`. For uploads, I'd have the client request a pre-signed URL and upload the image straight to object storage, so our servers don't carry the bytes.

**Interviewer:** Walk me through the design.

**Candidate:** Clients talk to a load balancer and stateless API servers. Photo metadata, owner, caption, storage key and creation time, goes in a database partitioned by photo ID; the follow graph in its own table with indexes in both directions. Images go to object storage, served through a CDN, with a few resized versions generated by a processing worker after upload. For the feed, when a photo is posted I'd publish an event, and fan-out workers push the photo ID into each follower's feed list in a distributed cache. Reading the feed is then one cache read plus a batched lookup of photo metadata.

**Interviewer:** What about someone with 50 million followers?

**Candidate:** Pushing to 50 million feeds per photo would be a huge write spike. I'd use a hybrid: above some follower threshold, say 100,000, don't fan out. When a user reads their feed, merge their pushed feed with recent photos from the few big accounts they follow. That keeps reads fast and avoids the write explosion.

**Interviewer:** And likes?

**Candidate:** A popular photo can get thousands of likes per second, so updating one counter row would be a hot spot. I'd record likes in a likes table keyed by photo and user, so each user can like only once, and maintain the count asynchronously: aggregate like events in a stream and update the count every few seconds. Users won't notice a count that's a few seconds behind.

**Interviewer:** What would break first if traffic grew ten times?

**Candidate:** The CDN scales; the fan-out workers and the feed cache would be first. I'd watch fan-out lag and cache memory, add workers, and partition the cache further. The metadata database also needs read replicas and a cache for hot photos.

**Interviewer's notes.** *Hire at mid-level. Scoped the problem crisply and made explicit assumptions. Estimates were correct and, importantly, used: object storage, CDN, read-heavy design all followed from them. Clean API with cursor pagination and direct uploads. Knew the push/pull hybrid for large accounts without prompting beyond the question. Asynchronous like counts was a good touch. Deep dives were adequate rather than deep; failure modes were not discussed until asked.*

## Mock 2: Distributed Cache (Senior)

**The prompt:** "Design a distributed in-memory cache that application servers across the company can use."

**Candidate:** Let me clarify the use: a shared key-value cache with get, set with a TTL, and delete, used by many services to reduce database load. Values up to, say, 1 MB. Is persistence required?

**Interviewer:** No, it's a cache. But a node failure shouldn't send a flood of traffic to the databases.

**Candidate:** Understood. Scale?

**Interviewer:** About 10 million operations per second and 30 TB of cached data.

**Candidate:** If each node has 256 GB of usable memory, 30 TB needs about 120 nodes for memory alone. At, say, 200,000 operations per second per node, 10 million needs about 50 nodes, so memory decides: around 120 nodes, more with replicas. Clients need to find the right node for each key without a central lookup on every request.

**Interviewer:** How?

**Candidate:** Consistent hashing with virtual nodes. Each client library holds the ring and hashes keys to nodes directly, so a request is one network hop. When a node is added or removed, only about 1/N of keys move, instead of almost all of them with hash mod N. Virtual nodes keep the load even; with around a hundred per node, the busiest node is within about 15% of its fair share. Ring membership comes from a configuration service backed by consensus, and clients watch it for changes.

**Interviewer:** A node dies. What happens?

**Candidate:** Its keys now map to the next nodes on the ring, which don't have them, so those requests miss and go to the databases. With 120 nodes that's under 1% of keys, which may be fine. If even that's too much for some databases, two options: replicate each key to two nodes, so a failure doesn't cause misses, at twice the memory cost; or, more cheaply, protect the databases with request coalescing, so concurrent misses for the same key cause only one database read.

**Interviewer:** Let's talk about hot keys.

**Candidate:** A key that's extremely popular, like a homepage configuration, overloads its node regardless of hashing. I'd detect hot keys by sampling requests, perhaps with a Count-Min sketch, and then either replicate them to several nodes and let clients pick one at random, or cache them briefly inside the client library itself. A local cache of even a second absorbs most of the load.

**Interviewer:** How do you keep it consistent with the database?

**Candidate:** I'd recommend cache-aside to application teams: read from the cache, fall back to the database, and on writes update the database then delete the key. Deleting rather than setting avoids races between writers. TTLs bound any staleness that slips through. For stampedes when a hot key expires, add jitter to TTLs and use coalescing.

**Interviewer:** Memory management on each node?

**Candidate:** LRU eviction per node, with memory allocated in size classes to limit fragmentation. Large values should be discouraged; I'd cap them and expose metrics on value sizes, hit rates and evictions per client, so teams can tune their usage.

**Interviewer's notes.** *Strong hire, senior. Drove the conversation and quantified everything: node count from memory versus throughput was exactly the right analysis. Clear explanation of consistent hashing and why virtual nodes matter, with numbers. Handled node failure with two options and their costs. Good depth on hot keys and stampedes. Thought about the platform's users (guidance, limits, metrics), which is a senior signal.*

## Mock 3: Online Auctions (Senior)

**The prompt:** "Design an online auction site. Sellers list items; buyers bid until the auction ends; the highest bid wins."

**Candidate:** Key requirements as I understand them: list items with an end time; place bids; show the current highest bid in near real time; at the end, determine the winner and start payment. A bid must be higher than the current highest by a minimum increment. Is that right?

**Interviewer:** Yes. Popular auctions get very busy in the last minute.

**Candidate:** So the hard parts are correctness of bids under heavy concurrency, especially at the end, and fairness of the end time. Let me estimate. Say a million active auctions and 5,000 bids per second normally. A hot auction might receive a few thousand bids in its final minute, so per-auction bursts of 50 to 100 bids per second.

**Interviewer:** OK.

**Candidate:** For correctness, each auction's state, current highest bid and bidder, version and end time, lives in one row or one partition. Placing a bid is a conditional update: "set highest to X if X ≥ current + increment and now < end time and version = v". If the version changed, re-read and re-check. That guarantees no two bids both win, the same optimistic approach as booking a seat. Every accepted and rejected bid is also appended to a bid log, for audit and disputes.

**Interviewer:** Couldn't contention at the end make most bids fail and retry?

**Candidate:** At 100 bids per second on one auction, conditional updates on a single row are fine for a modern database. If an auction were much hotter, I'd route all bids for that auction to a single owner process that applies them in order from an in-memory queue, writing results durably. That serializes them without lock contention. Partitioning auctions across owners by auction ID keeps it scalable.

**Interviewer:** How do bidders see the current price?

**Candidate:** Clients on an auction page subscribe over WebSockets or Server-Sent Events. When a bid is accepted, an event goes to a pub/sub channel for that auction, and gateways push it to subscribers. A slow or reconnecting client fetches the current state on reconnect. Price updates may lag by a fraction of a second, but the decision about a bid is always made against the database, never against what the client saw.

**Interviewer:** What about the end time?

**Candidate:** The server's clock decides, and bids are timestamped on arrival at the bidding service, not by clients. To prevent last-second sniping, many auction sites extend the end time by a minute or two whenever a bid arrives near the end; that's a product decision I'd raise with you. Closing is a scheduled job per auction, using leases so exactly one worker closes it, with an idempotent close operation: determine the winner from the final state, mark the auction closed, and start payment with an idempotency key.

**Interviewer:** What if the closing job runs twice?

**Candidate:** The close is a conditional update from "open" to "closed", so the second run sees it's already closed and does nothing. Payment uses the auction ID as its idempotency key, so it can't charge twice.

**Interviewer's notes.** *Hire, senior. Immediately identified correctness under contention and end-time fairness as the hard parts. Conditional updates with versions, plus the single-owner serialization option for extreme hot spots, were well reasoned. Separated the real-time display path from the authoritative decision path. Good handling of closing with leases and idempotency. Could have estimated storage and discussed search for listings, but the focus on the hard parts was right.*

## Mock 4: Global Configuration Service (Staff)

**The prompt:** "Design a service that delivers configuration and feature flags to all services in a company, across several regions."

**Candidate:** Let me understand the users and the risks. Engineers change configuration, such as feature flags, timeouts and rollout percentages, and thousands of services read it. The biggest risk with configuration is outages caused by bad changes, so safety matters as much as speed. Requirements I'd propose: changes reach all services within seconds; reads are local and never block a service; changes are versioned, reviewed and can be rolled back; and staged rollout by region. Does that match your intent?

**Interviewer:** Yes. Assume 50,000 service instances and a few hundred changes a day.

**Candidate:** Then the write rate is trivial and the read rate is enormous but can be served locally. Each instance reads flags on every request, maybe millions of reads per second in total, so reads must come from memory inside each process, not from a network call. The design is about distribution and safety, not throughput.

**Interviewer:** Go ahead.

**Candidate:** The source of truth is a strongly consistent store, replicated with consensus across regions, holding versioned configuration. Every change goes through an API that validates it against a schema, records who made it, and assigns a new version number. Each region has a distribution layer: a set of servers that receive changes and push them to a lightweight agent on every host, over long-lived connections. The agent writes the configuration to local disk and exposes it to the process through a library that keeps it in memory. If everything upstream is down, services keep running on the last configuration they have, read from local disk at startup.

**Interviewer:** Why not let services read from the central store directly?

**Candidate:** Fifty thousand instances polling a consensus store would overload it, and a configuration outage would become an outage of every service. Pushing through regional caches and local agents makes reads independent of the central store's availability. That's the most important design decision here: the configuration system must never be on the critical path of a request.

**Interviewer:** How do you make changes safe?

**Candidate:** Several layers. Validation: schemas and type checks, plus custom checks such as "a timeout can't be zero". Review: two-person approval for critical keys. Staged rollout: a change applies to a canary set of hosts, then one region, then everywhere, with automatic checks of error rates between stages, and automatic rollback if they rise. Every change is a new version, so rollback is just "make version N-1 current again". And a kill switch per feature flag.

**Interviewer:** Two engineers change the same flag at once.

**Candidate:** The API uses optimistic concurrency: each change states the version it was based on, and the store rejects it if the version has moved on, so the second engineer sees the conflict and re-applies their change knowingly. No silent overwrites.

**Interviewer:** How would you migrate the company onto this from scattered config files?

**Candidate:** Gradually. First, ship the client library with a fallback to the existing files, and mirror existing configuration into the new store read-only. Then move teams one at a time to make changes through the new system, starting with low-risk services. Measure propagation time and staleness per host, and only remove the old files when every reader is on the new path. I'd also define ownership: each configuration namespace belongs to a team, which controls approvals.

**Interviewer:** What would you monitor?

**Candidate:** Propagation delay per region, the version each host is running, so we can see stragglers, validation failures, rollbacks, and the error-rate checks between rollout stages. And a dashboard that answers "what changed in the last hour?", the first question in most incidents.

**Interviewer's notes.** *Strong hire, staff. Reframed the problem around its real risk, configuration-caused outages, before designing. Correctly identified that reads must be local and the system off the critical path; designed push distribution with local caching and last-known-good fallback. Safety mechanisms were comprehensive and practical. Covered concurrency, migration, ownership and incident response, which is exactly the breadth expected at staff level.*

## What the Four Interviews Have in Common

- Every candidate **agreed on scope** and stated assumptions before designing.
- **Estimates drove decisions**: object storage and a CDN; node counts from memory; a write rate too small to matter.
- Each identified **the hard part of that particular system** early and spent their time there.
- **Trade-offs were explicit**: replication versus memory cost, push versus pull, conditional updates versus single-owner queues.
- The more senior the level, the more the conversation covered **failure, safety, operations and migration**.

## Key Takeaways

- Practice full interviews out loud, with a timer, on prompts you haven't studied.
- Scope first, estimate next, and use the numbers.
- Find the hard part of the system and go deep there.
- At senior and staff levels, discuss failures, safety, operations and rollout without being asked.
